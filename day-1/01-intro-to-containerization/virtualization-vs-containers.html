Slide 1 — Introduction

Virtualization vs Containers:
The Evolution of Application Deployment

Understanding the journey from physical servers to modern containerized deployments.

Why do we need virtualization?

Before Virtualization

  • One application per physical server
  • Low hardware utilization
  • Expensive infrastructure
  • Difficult scaling
  • Resource waste

Virtualization introduced

  • Multiple Virtual Machines (VMs) on one physical server
  • Better resource utilization
  • Isolation between workloads
  • Easier infrastructure management

Containers evolved to solve

  • Faster startup
  • Smaller footprint
  • Better portability
  • Cloud-native deployments
Virtualization solved the problem of inefficient hardware usage. Containers took the next step by virtualizing the operating system instead of the hardware, making applications much lighter and faster to deploy.

Slide 7 — Container Lifecycle

Container Lifecycle

Understanding how containers move through different states.
Docker Image │ ▼ docker run │ ▼ Created │ ▼ Running │ ┌────┴────┐ │ │ Pause Stop │ │ └────┬────┘ ▼ Restart │ ▼ Running │ ▼ Remove

Lifecycle States

  • Image — Read-only blueprint
  • Created — Container exists but isn't running
  • Running — Application is executing
  • Paused — Processes temporarily suspended
  • Stopped — Execution ended, data preserved
  • Removed — Container deleted
Important Concept: Containers are ephemeral.
  • They can be created quickly.
  • They can be destroyed at any time.
  • Persistent data should live outside the container (volumes, databases, cloud storage).
This is one of the most important concepts before introducing Kubernetes or OpenShift. In production, if a container crashes, the orchestrator typically creates a new one instead of repairing the old one.
